在换过十几个笔记软件之后，我最终把主力写作和知识沉淀的阵地停留在了 [Obsidian](https://obsidian.md)。

这篇博客记录我使用 Obsidian 的思考模型与工作流，以及在长期使用中发现的那些被许多博主刻意忽略的缺陷。

## 哲学基石：本地优先

市面上绝大部分笔记工具（如 Notion、Craft）本质上是“云优先”的数据库服务。数据被储存在远程服务器上，受制于网络环境、供应商的商业策略以及随时可能发生的服务端断联。

Obsidian 的哲学彻底反转了这种依附关系：它把笔记还原为纯粹的纯文本 Markdown 文件。文件夹就是你的知识库，文件就是你的知识载体。即使二十年后 Obsidian 这家公司不复存在，你的笔记依然可以用任何文本编辑器直接打开。

> [!NOTE] 数据主权原则
> 不要把你的思考托付给一个无法一键导出纯文本的黑盒系统。工具会老去，格式会过时，但纯文本是数字世界的花岗岩。

## 双链笔记的迷思与真相

### 不要过早建立网状连接

初学者最容易陷入的陷阱，是在刚建库的前几周狂热地为每一个名词打上 `[[双向链接]]`，陶醉在星系一般绚丽的知识图谱里。但这种图谱除了发在社交媒体上满足虚荣心之外，对真正的理解往往毫无用处。

网状结构应该像自然界中的地脉一样，是由多条思路多次交叉后自然沉淀出来的，而不是人为强行编织的假象。如果你不能用一句话概括两个笔记之间的具体逻辑关联，那么这个双链就不应该存在。

### 卡片盒笔记法的改良

卢曼的卡片盒笔记法被很多生产力网红神化了。在实际日常中，过度细碎的“原子化”笔记会导致上下文割裂。我的改良做法是：以主题为单位撰写长篇文档，仅将具有复用价值的核心观点提炼为概念卡片。

## 我的核心工作流

一个高效的系统必须抵御“折腾插件”的诱惑。我的 Obsidian 库只保留四个核心插件：

- **Dataview**：用于对具有 YAML frontmatter 的笔记进行聚合查询。
- **Omnisearch**：基于 BM25 算法的高性能本地语义检索，支持搜索 PDF 与图片文字。
- **Canvas**：官方内置的白板，用于结构化梳理文章大纲与架构图。
- **Git 自动同步**：通过 GitHub 私有仓库实现全平台多端版本控制与防灾备份。

### 查询聚合代码示例

下面是我在每日汇总页使用的 Dataview 查询语法示例：

```dataview
TABLE file.mtime AS "最后修改", tags AS "标签"

```

### 定时同步备份脚本

为了避免多端协同冲突并保有完整的历史版本记录，我使用如下 Shell 脚本进行定时增量防冲突同步：

```bash
#!/usr/bin/env bash
# Obsidian 知识库定时增量防冲突同步脚本
VAULT_DIR="$HOME/Documents/Vault"
cd "$VAULT_DIR" || exit 1

# 抓取远端修改并尝试自动变基
git fetch origin main >/dev/null 2>&1
git rebase origin/main >/dev/null 2>&1

# 如存在本地改动则提交并推送
if [ -n "$(git status --porcelain)" ]; then
  git add -A
  git commit -m "auto: vault snapshot $(date '+%Y-%m-%d %H:%M:%S')"
  git push origin main
fi
```

## Obsidian 的缺陷

没有完美的工具。在使用 Obsidian 两年后，我对它的缺点同样心知肚明：

| 维度 | 缺陷现象 | 应对策略 |
| :--- | :--- | :--- |
| 移动端体验 | 启动缓慢，插件过多时内存占用高，输入法光标偶发跳跃 | 移动端仅用于速记收集，定期在桌面端归档整理 |
| 协作难度 | 纯文本模式缺乏成熟的实时多人协同光标体验 | 对外协同优先使用 Google Docs，定稿后归档回本地 |
| 排版上限 | 原生 Markdown 缺乏多栏混排和复杂表格语义支持 | 通过自定义 CSS 片段或导出到专业排版平台渲染 |

## 总结

知识管理工具的最终目的不是为了展示自己“收集了多少知识”，而是为了在需要调用的时候能够快速检索，并在思考碰撞中产出自己的表达。
